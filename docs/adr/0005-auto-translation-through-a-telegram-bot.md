# Auto-translation goes through a Telegram bot, and moves WhatsApp Web to the Translated Chat

The user talks with a contact who writes another language. They want to read and answer that one Chat in their own language from their phone, the way they already do for kaufmich in the Kolja extension: new messages arrive in a Telegram bot, translated, and what they write to the bot is translated back and sent. We built the same thing here, reusing Kolja's Telegram design (long polling from the background worker, one bot per program, a one-time pairing code so only the user's Telegram chat is obeyed, five wrong messages void the code).

Decisions, as the user chose them:

- **WhatsApp Web is the only way in.** WhatsApp has no API for a personal account, and WhatsApp Web only puts the open Chat's messages in the page; the Chat list shows a one-line preview of the others. So the Chat Watcher **reads from the Chat list when it can, and switches WhatsApp Web to the Translated Chat only when it must**: when a row's unread count (the badge's number, read in any language) goes up by one and the row shows that message as plain text, the message is taken from the row (its `title` holds it in full), with no switch and no read receipt; when the count goes up by more (the row shows only the last message) or the message isn't plain text (an icon beside it: a photo, a voice note), the Chat is opened and read, and WhatsApp Web stays there. When the Chat is opened later, messages already forwarded from the list are matched by text and not forwarded again. A row that changes without its count going up (typing, a message sent from the phone) is left alone. Sending switches to the Chat, types into the message box (`execCommand('insertText')`, so the editor gets real input events; it applies them a moment later, so the extension waits for the text), sends, and switches back to the Chat that was open. Rejected: requiring the Chat to stay open (simpler, but the user wanted to keep using WhatsApp Web); reading WhatsApp Web's internal JavaScript modules (no stable interface, breaks with every update).
- **Replies are sent straight away**, without a confirmation tap. The bot then says what was sent, with a back-translation from a separate call, so a mistranslation is seen at once. Kolja asks for a tap before every send; here the user preferred speed.
- **Google Translate's free endpoint by default**, an LLM with the user's own key (any OpenAI-compatible API, OpenRouter by default) as an option. Google needs no setup; the LLM handles tone and slang better.
- **Several Translated Chats**, each with its contact's language fixed in the settings (not detected). Incoming messages are translated from whatever language Google detects, and arrive in the one Telegram chat under their Chat's name.
- **A reply picks its Chat by what it replies to.** Swipe-replying to a forwarded message (or to the bot's answer about a send) goes to that message's Chat. A plain message goes to the Chat that last wrote or that the user last answered; with no such Chat and more than one configured, it is not sent and the bot asks for a reply. The bot's answer always names the Chat. Rejected: requiring a reply for every message (safer, slower), and one Telegram forum topic per Chat (cleanest to use, but needs a group with Topics and the bot as admin).
- **Only new messages** are forwarded. When the Translated Chat is first seen, everything loaded counts as seen; later, only incoming messages after the last seen one or after the user's own last message, and only while the message list shows its newest messages, so history loaded by scrolling up is never forwarded. Ids seen are kept in `chrome.storage.local`, and each message is forwarded at most once.
- **A Chat is known by its name, and checked by its messages.** WhatsApp Web shows no stable Chat id, and message ids no longer contain one, so a Translated Chat is found by name, which any other Chat can take (a group member can rename a group). Two Chats of that name in the Chat list: neither is opened nor read. And a Chat opened under the name must show at least one message already seen there (message ids are unique; another Chat can't show them): otherwise nothing from it is forwarded, no reply is sent to it, and the user is told once in Telegram. If the real Chat had so many new messages that no known one is loaded any more, removing it in the options and adding it again starts it afresh. Rejected: reading the Chat's id from WhatsApp Web's internal modules (no stable interface). A message forwarded from the Chat list row, without opening the Chat, can't be checked this way; a reply to it is.
- **Never during a Chat Record.** Switching Chats would spoil it, so the Chat Watcher does nothing while one runs, and replies fail with a message asking to send again.

Accepted costs:

- **WhatsApp Web still moves under the user sometimes**: for several messages at once, or a photo or voice note, it switches to that Chat and stays; a reply switches there and back. Badges that were already there don't count, so badges WhatsApp Web doesn't clear in a background tab can't make it switch back and forth.
- **In test mode**, the user's own messages raise no unread count, so they are forwarded only while their Chat is open.
- **A plain message can reach the wrong Chat** when another Chat writes just before it is sent. The bot's answer names the Chat it went to. A reply refuses to send if the message box already holds text the user typed.
- **Read receipts.** Opening a Translated Chat can mark its messages as read, though the user hasn't read them yet in Telegram.
- **Message text leaves the computer.** The Translated Chats' new messages and the user's replies go to Telegram and to the translator (Google, or the LLM provider). Nothing from other Chats does. Before this, the extension made no network requests.
- **Google's endpoint is unofficial**: it may be rate-limited or change without notice; then incoming messages are forwarded untranslated with a warning, and replies are not sent.
- **Secrets in local storage.** The bot token and the LLM key sit in `chrome.storage.local`, readable by anyone with access to the Chrome profile, as in Kolja.
- **The selectors are unverified.** The Chat list, unread badge, search box, message text and send button selectors (`selectors.ts`) follow WhatsApp Web's commonly described structure and synthetic snapshots; they need checking against the real page.
- **Background tabs.** Chrome slows a background tab's timers to once a second (once a minute after a few minutes hidden) and runs no animation frames there, so the Chat Watcher's waits watch the page for changes (`MutationObserver`) instead of polling.
